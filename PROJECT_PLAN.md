# Portfolio Diversification Dashboard, Project Plan

## Purpose
A tool to give insight into portfolio diversification: which regions, which sectors, which equity types (stock/ETF/commodity). Not a live price tracker, not a performance tool. Built from DEGIRO CSV exports.

## Build order
1. **Local version first.** Adds snapshot saving and a comparison tab between two dates. Uses SQLite. Single user, no auth needed.
2. **Public version later.** Same enrichment pipeline, wrapped statelessly, no database, no saving. Hosted on Streamlit Community Cloud so friends can upload their own CSV and get a snapshot with nothing stored.

## The DEGIRO CSV format
Columns: Product, Symbool/ISIN, Aantal (quantity), Slotkoers (close price), currency, local value, Waarde in EUR. Uses European number formatting (comma as decimal separator). No ticker symbol and no asset type in the raw export, both need to be resolved separately. One row is a cash line with no ISIN.

## Enrichment pipeline (per position)
1. Resolve ISIN to a Yahoo Finance ticker (via Yahoo's search endpoint). Fail gracefully when it can't be resolved, don't crash the whole run.
   - **Real bug found and fixed -- confirmed by Matteo on the live Streamlit Cloud deploy**: this lookup (`yf.Search`) failed outright for AST SpaceMobile (`US00217D1000`), shown in the app's own "could not be fully resolved" expander -- while resolving correctly every single time in local testing. Same root cause as the Rebalance-tab crash and the ETF sector-data gap above: Yahoo Finance calls are intermittently unreliable specifically from Streamlit Community Cloud's shared IP range, not from a home connection. `_resolve_quote` now retries up to 3 times with a short backoff (0.75s, doubling) before giving up -- retrying on an *empty* result, not just a raised exception, since Yahoo's rate-limit response for this endpoint has been observed to come back as a quietly empty list rather than an error. Bounded, not unbounded: a genuinely unresolvable ISIN still fails within a couple of seconds rather than stalling the whole enrichment run. Verified in bare mode: a mocked transient failure (empty on the first 2 attempts, succeeding on the 3rd) recovers correctly; a mocked permanent failure still gives up cleanly after exactly 2 retries; the real live lookup for `US00217D1000` still resolves on the first attempt, unaffected.
2. Pull asset type via `quoteType` (Stock, ETF, etc). This needs to generalize to any friend's holdings, not just mine, so don't hardcode by product name where avoidable.
3. Pull sector for stocks directly from Yahoo Finance. For ETFs, use `funds_data.sector_weightings` for a look-through breakdown instead of a single sector.
   - **Fallback when Yahoo's own sector lookup comes back empty** (built, follow-up to the Rebalance-tab crash below): `_justetf_sector_weights(isin)` re-uses the same justETF `get_etf_overview()` call already made for region/TER (see step 4/6), pulling its `sectors` field instead -- confirmed via a live call this data is genuinely there and free, no extra network round trip needed on top of what's already fetched for region. Only tried when `fund.sector_weightings` is empty, so the normal (Yahoo-works) path pays zero extra cost -- verified directly: mocking a working Yahoo response and spying on the fallback function confirms it's never even called in that case. justETF's own sector taxonomy (ICB-based: "Finance," "Consumer Non-Cyclicals," "Business Services," etc.) differs from Yahoo's GICS one that stocks use, so results are remapped through `_JUSTETF_SECTOR_MAP` onto the same Title Case buckets (a few justETF categories folding into one GICS bucket where GICS doesn't split as finely, e.g. both "Consumer Cyclicals" and "Consumer Services" -> "Consumer Cyclical") -- otherwise a fallback-sourced ETF wouldn't sum into the same buckets as everything else on the Allocation donut. Deliberately *not* cached to a CSV the way region/TER are: caching a fallback value would mean it stays stuck even after Yahoo recovers, defeating the point of preferring Yahoo whenever it actually works. Verified against real data (Vanguard FTSE All-World, `IE00BK5BQT80`): justETF's 13 raw categories correctly collapse to 11 GICS buckets summing to exactly 1.0.
4. Pull region:
   - **Stocks**: headquarters country via Yahoo Finance `.info`. Known limitation: this picks up legal domicile, not actual business exposure (e.g. Nebius is HQ'd in Amsterdam but isn't a Dutch business). Treated as an accepted approximation for stocks, edge cases are rare.
   - **ETFs**: real country look-through via the `justetf-scraping` package (unofficial, scrapes justETF), keyed by ISIN. This is the accurate source since it reflects actual fund composition, not domicile or listing exchange. Yahoo Finance has no country/region weighting field for funds, and Financial Modeling Prep's equivalent endpoint requires a paid plan, so justETF is the only free, precise option for European-listed UCITS ETFs.
   - Results are cached in `fund_regions.csv` (ISIN, Country, Percentage), one scrape per ISIN, ever, reused on every later run instead of re-scraping. Wrap the scrape call in try/except; on failure, mark region as "Unknown" rather than crashing the pipeline. Only call this for rows where AssetType is ETF.
5. Pull top holdings for ETFs (`funds_data.top_holdings`) to support the overlap check.
6. Pull TER (total expense ratio) for ETFs from the same justETF `get_etf_overview()` call already used for region -- it's a plain percentage number (`0.2` meaning 0.20%, not a 0-1 fraction). Cached separately in `fund_ter.csv` (ISIN, TER), same one-scrape-ever policy as region, but checked independently rather than gated on the region cache: an ISIN whose region was cached before TER was tracked still gets a one-time backfill scrape instead of permanently missing TER. Shown in the Positions tab, alongside a small "ⓘ" link to that ETF's justETF page (`https://www.justetf.com/en/etf-profile.html?isin=...`), both only when the top-of-page Scope toggle is set to ETFs only -- in whole-portfolio scope the table also has stocks/cash, which have neither. The icon is its own narrow column immediately after Name, as close to "attached to the name" as `st.dataframe` actually allows -- a single cell can only be one column type (text, link, ...), not a plain-text name plus a separately-clickable icon layered inside it.
7. Pull trailing-12-month dividend yield, for both stocks and ETFs -- **not** from Yahoo's `dividendYield`/`dividendRate` `.info` fields, which came back `None` for a real distributing ETF (VWRL.AS) in a live test, unreliable for ETFs specifically even though they work for stocks. Instead, derived from the per-payment `.dividends` history: sum whatever was paid in the last 365 days, divide by the current price (`fast_info.last_price`). Per-share dividend and price are in the same native currency, so this ratio is currency-agnostic -- no FX conversion needed to turn it into a EUR income estimate, just multiply the yield fraction by a position's already-EUR `value_eur`. Not cached (cheap enough per run, and dividend history changes over time unlike region/TER which are static fund facts). `None` means the lookup failed; `0.0` is a genuine result (no dividends paid in the last year -- e.g. an accumulating ETF that reinvests internally, or a stock that just doesn't pay one) and is not treated as an error.

## Dashboard features
- **Positions table** (now on the Overview page, side-by-side with a compact Allocation donut rather than in its own tab -- see Overview & Allocation pages, below): name, type, quantity, **Total Value**, % of portfolio, both formatted with an actual €/% sign and exactly 2 decimals (see European number formatting, below, for why these columns are the one place that isn't `formatting.py`-driven). Paginated (10 rows by default) with a "Show more" / "Show less" toggle button below and right-aligned under the table, instead of a fixed-height scrolling table. The *entire* table is always sent to the widget, collapsed or not -- `st.dataframe`'s column-header sort is client-side only, so if the collapsed view only ever sent the first 10 (unsorted) rows, sorting could only reorder that arbitrary slice and could never surface a genuinely-larger row from beyond the cutoff. `height` alone implements "collapsed" (tall enough to fit ~10 rows without scrolling); sorting while collapsed and wanting to see past row 10 now means scrolling within the table, the necessary trade-off for the sort itself to be correct rather than merely correct-looking on whatever was sent. In ETFs-only scope, two extra columns appear: TER and a small "ⓘ More info" link out to that ETF's justETF page (see Enrichment pipeline step 6) -- absent in whole-portfolio scope, since stocks/cash have neither.
  - **Value (per-unit price) -- added, then removed**: briefly had a `value_eur / quantity` per-unit-price column, hidden by default and revealed via a checkbox above the table. Along the way, discovered `st.dataframe`'s own built-in column-visibility toolbar menu (a separate, always-present icon in the table's own corner, not something this checkbox controls) only flips a column's internal `hidden` flag without touching column order (confirmed by reading the compiled frontend bundle's `showColumn` handler) -- so a column revealed through *that* menu always lands wherever the frontend's default position is, and that same menu also lets the pandas row index (labeled `(index)`) be toggled back on despite `hide_index=True`. There's no public `hidden` param on `st.column_config.NumberColumn`/`Column` in the installed version either, so omission from `column_order` was the only way to hide a column at all -- the checkbox worked around this by rebuilding `column_order` by hand each render. Removed at Matteo's request; the column, its checkbox, and the `unit_price` computation are gone from `views/positions.py` entirely (not just hidden) -- if it comes back, the toolbar-menu pitfall above is worth re-reading first.
  - **Narrower by design**: Type keeps a fixed `width=90` (short, fixed-vocabulary content: "Stock"/"ETF"/"Cash"). Quantity/Total Value/% of portfolio are sized by a small `_header_width(label)` helper instead of an eyeballed pixel number -- `round(len(label) * 7.7 + 24)`, i.e. the header text's own character count times an average glyph width plus fixed padding for the cell margin and sort-arrow gutter, calibrated against "Type" (4 chars) reading comfortably at 55px. Matteo asked for these three specifically to match their column *name's* length, so the width is genuinely derived from the label text rather than a number that happened to look right for one label and wrong for the next. Only Name is left unconstrained, since product names vary a lot in length (e.g. "iShares Core MSCI EM IMI UCITS ETF USD (Acc)") and everything else is short.
  - **`width="stretch"` vs `"content"` -- settled back on `"stretch"`**: briefly switched the table to `width="content"` (sizes to just its own columns) specifically to stop `"stretch"`'s default behavior of filling the whole positions column and pulling the tight pixel widths above back out wide. That traded one problem for two others Matteo then flagged: with the table no longer filling the column, freeing up width (e.g. collapsing the sidebar) left a dead gap next to the table instead of the table using it, and the "Show less" button -- positioned via a plain `st.columns([7, 1])` split *of the column's* width -- ended up floating to the right of the table's real (narrower) edge rather than sitting under it, since that split assumes the table fills the column. Back on `"stretch"` fixes both: the table genuinely fills the column again (matching what the button's column split assumes), and freed-up space gets used instead of left blank. The tradeoff, confirmed by reading the compiled frontend bundle: `"stretch"` gives every non-pinned column an equal `grow` share of the leftover space, fixed pixel widths included, not just Name -- so the tight widths above are a floor, not a hard cap, once there's slack to fill. Accepted as reasonable since the floor values are now genuinely tight (header-fit, not the old oversized "small" preset), so the growth reads as normal column padding rather than the original "too wide" complaint.
- **Allocation** (the full version described here now lives on its own Allocation page, reached via "Show more" from the Overview page's compact donut -- see Overview & Allocation pages, below): one interactive donut chart (`components/donut_chart.py`, reusable, portfolio-agnostic) instead of several static side-by-side pie charts. A row of segmented-control buttons above it (name text only, no radio-button circles) switches the dataset -- Type, Positions, Sectors, Regions, Countries, Currencies, i.e. every view we actually have data for (Industries and Market Cap were on the original wishlist but dropped: no per-security industry classification is pulled, GICS sector only, and no market cap field is pulled in enrichment either -- shown empty would be worse than not shown). All six views respect the top-of-page Scope toggle (ETF-only vs. whole-portfolio): Sectors/Regions/Countries via `sector_region_source`, Type/Positions/Currencies via `display_source` -- the same split `concentration_flags` already used, applied consistently everywhere rather than only on the sector/region-shaped views. The center of the donut is a dark info-card (small gray label, large bold euro figure) showing the current view's total -- and, on hovering a slice, that slice's own label/value instead, reverting on mouse-out. A holdings list sits beside the donut, visually separated by a divider line (same component, same data): name, a thin weight bar colored to match its slice, the percentage, and the euro amount. The list is fixed to the donut's own height and scrolls internally (however many rows a view has, e.g. 30 countries) rather than growing the whole component taller -- the donut's position and size stay constant across every view. Hovering either side highlights the same item on both: every *other* slice fades to a low opacity rather than the hovered slice pulling outward or moving, and the matching list row's name goes bold in full ink color while the rest stay muted -- no small color-dot marker for "this one's selected," the name text itself carries that distinction, with color-as-identity living on the weight bars instead. This all has to be instant with no server roundtrip, which rules out `st.plotly_chart`/`px.pie` (Streamlit's wrapper has no client-side hover hooks -- reacting to hover would mean a full rerun per mouse movement) and rules out splitting the chart and list into separate Streamlit elements too (syncing hover state across two independent components isn't practical without a server roundtrip either). Built as one raw Plotly.js + plain-HTML-list bundle in a single `st.components.v1.html()` call, deliberately *not* the newer `st.iframe()`: this briefly ran on `st.iframe()` to dodge the deprecation warning, but `st.iframe()` hardcodes `scrolling=True` on the underlying `<iframe>` with no way to disable it, which caused a spurious *outer* scrollbar around the whole chart+list block on top of the list's own intentional one whenever rendered content came out even a pixel taller than the declared height. `components.v1.html()`'s `scrolling` parameter defaults to False, which crops overflow instead of ever showing a scrollbar -- a hard guarantee, not just a smaller chance of the bug -- so the deprecation warning is the accepted tradeoff. The fade/highlight/center-text-swap logic is wired up entirely in JS and shared between the chart's hover events and the list rows' mouseenter/mouseleave -- Python only decides which dataset to hand the whole component. Uses the same colorblind-safe categorical palette and light/dark theme-awareness as the rest of the app, cycled out to one color per slice up front so the donut and the list bars always agree on which color is whose. Label text is escaped before being built into the list's HTML, since it comes from portfolio data (product names, sector/region buckets), not a trusted literal.
- **Concentration warning**: flag any position, sector, or region bucket above a threshold, each independently adjustable via its own sidebar slider (asset default 10%, sector default 25%, region default 40%). The region check uses continent-level buckets (same grouping as the Allocation tab's region pie chart), not raw countries -- a portfolio spread across many European countries shouldn't dodge the check just because no single country crosses the threshold. `continent_breakdown` keeps "Unresolved" (no region data at all -- e.g. a justETF overview with a genuinely empty countries list, hit for real testing an iShares Core S&P 500 UCITS ETF, IE00B5BMR087) and "Unknown" (a justETF scrape that errored outright) as their own buckets rather than folding them into "Other" alongside genuinely-classified-but-unmapped countries (Canada, Mexico, Australia, ...) -- conflating the two used to produce a false concentration flag ("Region Other is 57%") that was actually mostly one fully-unresolved ETF position wearing the same label as real, small countries. Respects the top-of-page Scope toggle: in whole-portfolio scope the asset check excludes ETFs (inherently diversified, not a concentration risk the way a single stock is) and sector/region cover the whole portfolio; in ETFs-only scope the asset check is skipped entirely (no per-position warning), and only sector/region concentration is checked, scoped to ETF-only value -- same as the Allocation tab's charts. Shown as an ambient banner, not a separate tab.
- **ETF overlap check**: compare individual stock holdings against each ETF's top holdings list. Surface direct overlaps plainly (e.g. "AAPL is in your Vanguard All-World holding, and you also hold it directly"). Not a full weighted recalculation, just a plain flag.
- **Target allocation drift**: let the user define a target mix (e.g. 70% stock / 20% bond / 10% cash, or target region weights), then flag drift from it. Reuses the same threshold-flag pattern as the concentration warning, just comparing actual vs. user-defined target instead of actual vs. a fixed cap. Works off a single snapshot, no history needed, so this fits both the local and public versions.
- **ESG score surfacing**: Yahoo Finance exposes `esgScores` per stock. Show as an optional column in the positions table, not as a judgment or rating, just visible data the user can choose to look at or ignore.
- **Dividends** (built): a collapsed `st.expander` below the tabs, not a tab of its own and not an extra positions-table column -- an occasional check, not a primary view the way Positions/Allocation/Rebalance are. Shows two headline `st.metric`s (estimated annual income, portfolio dividend yield) and a per-position table (name, type, annual income, yield), both scoped by the top-of-page Scope toggle the same way `display_source` already works everywhere else. Cash is excluded from the table (it can't pay dividends -- a zero row would be noise). Sourced from Enrichment pipeline step 7; a position showing €0 is either a genuine non-payer (accumulating ETF, non-dividend stock) or a failed lookup -- the two look the same here on purpose, since a failed lookup is already surfaced separately by the resolution-error expander above the tabs.
- **Exact breakdown totals**: `_weighted_breakdown()` (the shared engine behind sector/region/etc. breakdowns) used to silently drop value whenever a row's weights summed to slightly *over* 100% -- justETF's region percentages and Yahoo's sector_weightings both round at the source, so summing them doesn't always land on exactly 1.0, and the old code only added the leftover to "Unresolved" when it was positive, dropping negative leftover (overshoot) instead of counting it. That shrank the reported total by a different amount depending on which weighting source overshot, so e.g. the Sectors and Regions views could show visibly different totals (€9,220.32 vs. €9,219.84) for the same underlying holdings. Fixed by rescaling an overshooting row's weights down to sum to exactly 1 before distributing (undershoot still flows into Unresolved as before, since that's a real "not classified" signal, not rounding noise) -- every row's contribution now sums to exactly its own value_eur, so every breakdown's total exactly equals the sum of value_eur for its input rows, regardless of over- or under-100% weight sums.
- **European number formatting**: every euro value and percentage in the app -- the donut chart's center card and holdings list, `st.metric`, concentration/drift banner text, and the rebalance calculator's captions -- renders period-thousands/comma-decimal ("9.220,32"), not the US-style grouping Python's f-strings and Streamlit's built-in "euro"/"percent" `NumberColumn` formats produce by default. Centralized in `formatting.py` (`format_eur`/`format_pct`/`format_number`) rather than reformatted ad hoc at each call site. The donut chart is raw JS, not Python, so it mirrors this with `toLocaleString('nl-NL', ...)` rather than sharing `formatting.py` directly. **Interactive tables are the one exception**: the positions table and the rebalance calculator's buy/sell tables use genuinely numeric `NumberColumn`s instead of `formatting.py` strings. An earlier version pre-formatted those as European-style strings too, which broke the tables' click-to-sort (a string column sorts lexicographically -- "10" before "9" -- not numerically); a numeric column keeps sort correct regardless of which `NumberColumn` format is layered on top for display. Two different formats end up used, for different reasons:
  - The **rebalance buy/sell tables** use `format="localized"`, which renders using the *viewer's own browser locale* rather than a hardcoded one -- for a European-locale browser that's already period-thousands/comma-decimal, just not a hardcoded guarantee the way `formatting.py` is elsewhere. It has no currency symbol of its own (carried by the column label instead) and defaults to showing up to 3 decimals (Streamlit's own docs example: "1,234.567").
  - The **positions table**'s Value/% columns use a printf-style format string instead (`"€%.2f"`, `"%.2f%%"`), needed to get an actual euro/percent sign inside the cell and exactly 2 decimals -- neither of which `"localized"` can do. The trade-off: printf-style is hardcoded to comma-thousands/period-decimal with no locale awareness (Streamlit's own docs: "Use `,` for thousand separators"), so these two columns specifically show US-style grouping rather than the European convention used everywhere else. Percentage columns in both cases are pre-scaled to 0-100 before display, since neither `"localized"` nor a plain `%.2f` format multiplies by 100 itself.

## ETF-only view (built)
A "Scope" filter button (Whole portfolio / ETFs only) sits at the top of the page, right after the file is loaded. When ETFs only is selected, ETFs only is scoped through *everything*, not just the sector/region-shaped views: `sector_region_source` (Sectors/Regions/Countries) and `display_source` (the Positions tab table, and the Type/Positions/Currencies donut views) both switch to the ETF-only dataframe, so row counts, the "show all N positions" button, and every total shown reflect the filtered set too. (Earlier versions of this only scoped `sector_region_source`, leaving Positions/Type/Currencies silently showing the whole portfolio even with "ETFs only" selected -- fixed.) Renormalization to 100% of ETF-only value falls out automatically from the same weighted-breakdown math, no extra logic needed. ## Overview & Allocation pages (built)
A getquin-home-screen-style layout, at Matteo's request, replacing the old Positions/Allocation/Rebalance `st.tabs()`: the app is now genuinely multipage (`st.navigation` + `st.Page`), not a single script.

**Overview** (the default/landing page): Positions and a compact Allocation donut side by side via `st.columns([3, 2])` -- Positions still gets the wider column since it's a table, but not as wide as the original `[2, 1]` split: at 1:2 (33% of the row), the six-option view selector below wrapped "Currencies" onto its own second row once it didn't fit the remaining width, and `st.segmented_control` has no font-size/padding parameter to shrink the buttons instead -- `[3, 2]` (40%) gives it enough room to stay on one row. The compact donut has the same Type/Positions/Sectors/Regions/Countries/Currencies view selector as the full Allocation page (defaulting to "Type"), just its own `st.segmented_control` under a separate `"overview_donut_view"` session-state key -- deliberately not shared with the Allocation page's own `"donut_view"` key, so switching views here for a quick glance doesn't also jump the full page to a different view than it was left on. Uses `components/donut_chart.py`'s `render_donut(..., compact=True, height=320)` -- chart only, no holdings list, sized for the narrower column, and larger than its original `height=260` per Matteo's request. Its chart `<div>` is a fixed square (`width:{height}px`), not `width:100%` -- at 100%, Plotly centers the pie across the whole iframe, which itself stretches to the allocation column's full width. Fixing the pie's own footprint first, then centering *that* fixed box with plain flexbox (`display:flex; justify-content:center` on a wrapper `<div>`) is what makes it line up reliably with the view selector above -- which is centered the same way, wrapped in its own `st.container(horizontal_alignment="center")` on the Python side -- at any column width. Earlier attempts got this wrong twice: first a left-aligned selector next to a 100%-width-centered pie only lined up by coincidence at one column width and drifted apart at others (what Matteo first saw after collapsing the sidebar); then making the pie a fixed box but leaving it at its *default* left alignment matched the selector only if the selector was also left-aligned, which read as both being pinned to the column's left edge rather than centered in it (what Matteo then asked to have moved toward the middle). Centering both the same way is what makes "centered" and "aligned with each other" true at the same time, regardless of column width. A "Show more →" link (`st.page_link`) below it navigates to the **Allocation** page, which renders the exact same `render_allocation_tab` the old Allocation tab used -- view selector, full donut, holdings list, region caption, unchanged. Rebalance, still gated on Scope == "ETFs only", moved from its own tab to a plain section below the two-column layout on Overview -- a single lone tab wouldn't have made sense once Positions/Allocation stopped being tabs.

**`components/donut_chart.py`'s `compact` parameter**: added as a genuinely separate, smaller render path (its own `<script>` block, no list-building/list-hover JS at all) rather than restructuring the existing chart+list rendering to conditionally hide the list -- this file had an explicit "don't touch the confirmed-working chart/hover logic unless asked" note from earlier in the project; Matteo's request to add `compact` here counts as being asked, but the non-compact path itself is untouched, only a new branch was added ahead of it.

**Why a `state.py`, not just inlining setup in each page**: each page registered via `st.Page` is its own independent script run -- it doesn't inherit local variables from `app.py` or from any other page, only `st.session_state` persists across navigation. So the shared setup that used to run once at the bottom of `app.py` (loading, sidebar controls, the concentration/overlap/drift banners) now has to run at the top of *every* page instead. `state.py`'s `load_dashboard_state()` is that shared setup, called identically by both pages. This does mean the sidebar controls and banners are technically recomputed per page navigation -- deliberately accepted, per Matteo's own instruction ("correctness matters more here than shaving off recomputation") -- the actual expensive part (`load_and_enrich`'s Yahoo/justETF lookups) is still `@st.cache_data`-cached and shared across pages and reruns regardless, so what's "recomputed" is cheap pandas slicing plus re-drawing the same widgets so they show up identically everywhere.

**Testing**: no browser available in this environment (same constraint as the rest of local development here), so verification split two ways -- (1) both pages' render functions called directly in bare-mode Python (bypassing `st.navigation` itself, which needs a real browser session to route between pages), confirmed clean under both Scope settings, and confirmed the compact donut and the full Allocation page's donut pull from the exact same `donut_data_for_view("Type", ...)` call, so they're guaranteed to show identical data, not just visually similar data; (2) the real `streamlit run app.py` server started and its startup log checked clean, confirming `st.navigation`/`st.Page`/`pg.run()` itself doesn't raise -- the one part of this that bare-mode function calls can't exercise. Actually clicking through page-to-page navigation in a live browser is the one thing that couldn't be verified end-to-end.

## Rebalancing calculator (built)
Three related tools, all driven by a user-defined target distribution (by sector or by region). All three operate on ETFs only, since sector/region tilting only makes sense for funds, not individual stocks. Each uses the sector/region weight vectors already pulled per ETF in the enrichment step. Pure computation lives in `rebalance.py` (no API calls, no caching), tested against made-up weight vectors before ever touching live data. Both dimensions are bucketed down for a usable target form: Region uses continent-level buckets (United States/South America/Europe/Asia/Other, same map as the Allocation tab's Region view) instead of 30+ raw countries; Sector uses 6 buckets instead of all 11 GICS sectors: Technology, Healthcare, Financials, Consumer Goods (merges Consumer Cyclical + Consumer Defensive), Energy + Utilities (merged), and Other (Real Estate, Basic Materials, Industrials, Communication Services). Only the rebalance calculator is scoped down this way -- the Allocation tab's sector chart and the concentration/drift checks still use the full 11 GICS sectors.

In the app, this is its own "Rebalance" tab rather than a sidebar widget -- and only appears in the tab bar at all when the top-of-page Scope toggle is set to ETFs only (Positions / Allocation, or Positions / Allocation / Rebalance). Inside: a Sector/Region dimension toggle, then per-category number inputs (defaulting to current ETF-only weights, largest-remainder rounded) with a running total, wrapped in an `st.form` with a "Calculate" button so the solve only runs on submit, not on every slider tick. Below the form, a Buy-to-target / Quick rebalance / New ETF suggestions selector switches between views of the same calculated result.

All three tools trade in **whole shares**, not arbitrary EUR amounts -- you can only ever buy or sell an integer number of units. Quick rebalance uses `scipy.optimize.milp` (mixed-integer linear programming) directly; Buy-to-target uses a different, budget-aware two-step approach (see below) since it also needs to reason about a real EUR spending limit, which plain MILP-over-shares doesn't naturally express as "spend optimally, not maximally."

1. **Buy-to-target calculator** (built): whole shares to buy per ETF (new money only, nothing sold) to move the portfolio as close as possible to the target, spent from a budget rather than an unlimited amount. The Rebalance tab shows the portfolio's existing uninvested cash (parsed straight from the DEGIRO CSV's cash row) plus an "Additional cash to invest" input; together they form the budget.
   - **Solver**: a continuous `scipy.optimize.minimize(method="SLSQP")` solve first (objective: minimize squared distance to target; constraint: `sum(purchases) <= budget`, an *inequality* so unhelpful spending can be left on the table -- this is what makes it optimal rather than maximal use of cash; bound: purchases >= 0, buy-only). Run in fraction-of-budget units, not raw EUR, for the same finite-difference scaling reason documented on Quick rebalance's SLSQP history. The continuous result is then floored to whole shares, and the leftover change is spent greedily: repeatedly buy whichever single additional share (across held ETFs) improves fit the most per euro, until no affordable share meaningfully helps.
   - **Fallback when no additional cash is entered** (0 or empty): solve with just the existing cash first; if that leaves relative improvement under ~15% (or can't afford even one helpful share), it's not a useful suggestion, so re-solve against a hypothetical budget instead (25% of ETF-only portfolio value, a hand-picked constant) to avoid the extreme buy-only suggestions a heavily concentrated portfolio can mathematically require. Also reports "fully reaching this target would need about €X in new purchases" as context, from the same solver against a generous but finite ceiling (10x portfolio value) -- a truly *unconstrained* estimate isn't well-defined here, since buy-only rebalancing only ever dilutes existing holdings toward target asymptotically, so driving distance to exactly zero can require unbounded spend; an early version of this literally returned a "~€44 million needed" estimate for a moderately skewed target before this cap was added. If even that generous ceiling doesn't fully close the gap, the reported figure is flagged as a lower bound ("at least €X"), not an exact number.
   - **Feasibility caveat** (built): categories with target weight > 0 that no held ETF provides meaningful exposure to are flagged before the results table, not after, regardless of which budget path was used.

2. **Quick rebalance** (built): integer share deltas per ETF (buy and sell), no position sold below zero, net cash flow kept as close to zero as achievable in whole shares (exact zero usually isn't possible when ETFs have different prices) -- bounded to at most one share's worth of drift, and additionally given a tiny weight in the objective so the solver actually prefers the tightest cash-neutral option among ties, rather than any solution inside that bound. Solved via `scipy.optimize.milp`, with the category-fit objective expressed as **L1** (sum of absolute deviations from target), not least-squares (L2) -- `milp` only supports linear objectives, and least-squares is quadratic, so it can't be handed to it directly. L1 is the standard linear-programming-compatible stand-in, using one auxiliary variable per category (`t_j >= |gap_j|`, via two inequality constraints, then minimize `sum(t_j)`); it still finds the mathematically optimal whole-share combination, just under a different norm than a continuous solver would use.

3. **New ETF suggestions** (built): identifies the categories #1 and #2 can't reach and matches them against a small hand-built reference table, kept separate per dimension (sector categories vs. continent categories) since they use different vocabularies. Output stays categorical ("a Technology sector ETF would help close this gap"), never a specific ticker, to stay clear of investment-advice territory.

**Real bug found and fixed -- crashed the whole page on Streamlit Community Cloud, never seen locally**: `rebalance.build_weight_matrix` builds its category list from every held ETF's `enrich_sector_weights`/`enrich_region_weights` dict, unioned together -- if *every* held ETF's dict happens to be empty (Yahoo Finance's `funds_data.sector_weightings` lookup failing or coming back empty for all of them, more likely on a shared cloud IP getting rate-limited than on a home connection), the resulting matrix has zero columns, and the target-input row a few lines down calls `st.columns(min(4, len(matrix.columns)))` -- `st.columns(0)`, which Streamlit rejects outright (`StreamlitInvalidColumnSpecError`, needs >= 1), crashing the entire page rather than just this one tab. Naively generalizing that -- "restore current value whenever share count is nonzero" -- was tried first and immediately caught a worse problem before shipping: the *same* rebase chain actually spans **four** ISINs, not two, and a third (US8314454088, "Connexa," the original bug) also showed a nonzero "current" balance (750 shares) in this data, despite almost certainly being long superseded by the newer AIRWA ISINs -- DEGIRO's own ledger just never posted a zeroing event for it when the rename happened. Including it would have overcounted by roughly EUR 580, replacing a small, honest undercount with a much larger, confident-looking but wrong number. Fixed by detecting the collision instead of guessing: `portfolio_value_history` now resolves every ISIN's ticker up front and skips current-value restoration entirely whenever a ticker maps to more than one still-held ISIN at once (`ambiguous_tickers`) -- there's no reliable way to tell from this data alone which single ISIN (if any) is the real current holding, so the safe default (full exclusion) wins over a guess. For *this* portfolio, that means the fix correctly ends up doing nothing (all four AIRWA-chain ISINs collide on one ticker) -- the small residual gap stays, captioned, rather than being silently wrong in either direction. The general mechanism still helps any less tangled case: a single delisted/rebased ISIN with no ticker-sharing sibling now gets its current value back.

The restored amount only patches the *last* day of the returned value series (a small, deliberate jump, since the chart's history for that ISIN still can't be reconstructed) and is returned on its own (`current_value_addon`) so the caller can caption it rather than silently blend it in.

Once the SPLIT AANPASSING sign bug above was fixed, the AIRWA chain's real current share count turned out to be zero across all four ISINs -- the position is genuinely, fully closed, not ambiguous. So `current_value_addon` correctly stays EUR 0.00 for this portfolio either way (there was never really anything to restore), and the small residual gap against Matteo's real DEGIRO figures (~EUR 60 on Portfolio value, ~EUR 300 on Total P&L) was unchanged by this fix alone -- it wasn't from a phantom still-held position after all. Fully closed with FIFO realized-P&L tracking, below.

### FIFO realized P&L
Matteo's own suggestion, directly following from the AIRWA investigation above: since the position is now confirmed fully closed, its entire economic outcome already happened in cash and is sitting right there in the ledger -- no market pricing needed at all to know what it lost. **`cost_basis.py`** (new module): FIFO lot tracking per ISIN, computed purely from `ledger.extract_share_events`'s `cash_amount` (the ledger's own recorded cash effect of each row), not from yfinance:
- **`fifo_pnl(events)`**: a Koop (or a SPLIT AANPASSING opening leg) pushes a new lot; a Verkoop (or a closing leg) consumes the oldest lot(s) first and realizes proceeds-minus-cost -- FIFO, not average cost, per Matteo's explicit choice when this was first scoped. A SPLIT AANPASSING closing leg fully liquidates every open lot for that ISIN (confirmed exact in real test data -- a closing leg's described quantity always matched the ISIN's entire pre-close balance) and the paired opening leg starts a fresh lot on the *new* ISIN at that same cash, so a rename chain's cost basis carries through unbroken across however many ISINs it touches. Per-trade fees aren't attributed to one specific lot (their exact same-timestamp order relative to their trade isn't reliably recoverable once sorted, and Order Id isn't carried through event extraction) -- instead split between realized and unrealized by the fraction of that ISIN's lifetime volume sold vs. still held; the ISIN's *combined* total is exact regardless of how that split lands.
- **`total_pnl(events)`**: adds unrealized P&L (current market value minus remaining cost basis, for whatever open positions are still priceable) on top of `fifo_pnl`'s realized figure, to match the *shape* of DEGIRO's own "Total P&L" -- a lifetime total, not filtered by the chart's Timeframe selector.
- **Two real bugs found and fixed while building this, both via testing against the real ~600-row Account.csv, not caught by inspection alone**:
  - The FX conversion cache was built lazily around whichever row happened to trigger it first, covering only a ~2-week window around that one date. Since ISINs are processed via `groupby` (not chronologically), a later-processed ISIN with an *earlier* real date would look up a rate outside that cached window and silently get dropped -- confirmed zeroing out a real, unrelated Apple trade's contribution entirely. Fixed by building one full-date-range fx series per currency upfront, from the whole dataset's actual start to end, before the per-ISIN loop starts.
  - A short position (an option sold *to open* -- receiving premium with no prior purchase, confirmed real: `BESM P160.00 20FEB26`) has nothing in the lot queue to consume when it closes, so the original code's "while remaining and lots" loop did nothing and silently dropped the entire EUR 41.25 premium. Fixed: proceeds left over after the lot queue is exhausted are pure realized gain (there's no cost basis for a quantity never "bought" in this model), not discarded -- and a pure short's fees now count as 100% realized (`sold_fraction` forced to 1.0 when `total_bought` is 0 but something was sold) rather than landing in a nonsensical "unrealized cost" bucket for a position with zero open quantity.
- **Result on real test data**: Total P&L (lifetime) = EUR 1,579.00, against Matteo's real DEGIRO figure of EUR 1,634.55 -- a EUR 55.55 gap, down from the time-weighted approach's EUR ~300 gap. The residual is plausibly just daily-close-vs-real-time pricing noise across ten open positions, not a further bug -- not chased to the cent, since forcing an exact match would risk fabricating precision this pipeline's data (once-daily yfinance closes, not live quotes) doesn't actually have.
- **Shown as a "P&L (Timeframe)" line** in the Performance header. Originally shipped as a separate lifetime-only figure alongside the existing time-weighted EUR/% lines and a deposits breakdown -- Matteo then asked for the time-weighted lines and deposits breakdown removed entirely, and for P&L itself to follow the Timeframe pill instead of staying fixed at "all-time." Implemented via `cost_basis.windowed_pnl(events, start, end)`: two cumulative `total_pnl` snapshots (one as of the day before the window starts, one as of the window's last day) subtracted from each other -- `total_pnl` itself gained an `as_of` parameter for this (defaults to now, so old lifetime-total behavior is unchanged when called without one). "Max" naturally reduces to the old lifetime figure, since the "before" snapshot predates any account activity and comes back all-zero. Any open position that still can't be priced is flagged (`unpriced_open_isins`), not silently dropped from the total, same policy as everywhere else in this pipeline -- none occurred in real test data once the AIRWA chain turned out to be fully closed. Verified against real test data across all four windows (1M/YTD/1Y/Max), each landing on a distinct, plausible figure (e.g. 1M: EUR 391.11, Max: EUR 1,579.00 -- exactly matching the old lifetime-only computation, confirming the window-difference approach is consistent with it).
  - **% alongside the EUR figure** (built, per Matteo's request): `total_pnl_eur / baseline * 100`, where `baseline` is the window's *starting* holdings value -- already computed just above it for the chart's own dotted reference line and green/red line coloring, so this reuses that exact figure rather than introducing a second, differently-scoped one (e.g. cost basis, which would need its own separate FIFO walk per window and isn't otherwise on hand here). Same green/red coloring as the EUR figure, shown in parentheses right after it (e.g. "+EUR 437.94 (+5.1%)"). Skipped, not shown as a bogus 0% or an error, whenever the window starts at EUR 0 -- "Max" legitimately does, before the account's first purchase, and there's no meaningful percentage of nothing. Verified in bare mode: 1M showed "+5.1%" against real test data, Max correctly showed no percentage at all.
    - **Does this exclude cash additions? Yes, by construction, not by a separate check** -- Matteo asked specifically ("if my portfolio goes from 2,000 to 3,000 purely from adding 1,000, it should show 0% performance, not 50%"), since a naive `(current - baseline) / baseline` would *not* exclude it. The numerator here isn't that naive value delta, though -- it's `total_pnl_eur`, the FIFO windowed P&L already used for the EUR figure right next to it, which is cost-basis accounting: buying more shares adds equally to a lot's cost basis and its market value, netting to ~zero contribution to `unrealized_eur` at the moment of purchase (see `cost_basis.fifo_pnl`), only moving thereafter with real price change. So the % was already correct the moment the EUR figure was, with no extra code needed for this. Verified concretely against real test data (not just reasoned about): the 1M window had ~EUR 2,000 in genuine new purchases -- naive `(current-baseline)/baseline` gives +6.7% (deposit-inflated), `total_pnl_eur/baseline` gives the correct +5.1%; a narrow 2-day window isolating a single EUR 579.84 deposit-funded purchase with no other activity shows +0.54% (small residual real price movement in those 2 days), not the far larger swing a value-based % would show for a purchase that size.

**Performance (built)**: the first click on each Timeframe pill was taking 5-12 seconds -- confirmed and root-caused, not just guessed at, by timing `windowed_pnl` directly against the real Account.csv. Three separate, stacked causes, each only visible by profiling real calls, not by inspection:
  1. `performance._resolve_ticker` (an ISIN->ticker Yahoo *search*) and a ticker's currency (`fast_info.currency`, a separate live lookup) were re-fetched fresh every single time, for every open position, on every P&L snapshot -- both are static facts that don't change mid-session. Fixed with two plain module-level dicts (`_TICKER_CACHE`, `_CURRENCY_CACHE`) -- deliberately not `st.cache_data` for these two, since they're cheap, tiny, and don't need its hashing/invalidation machinery, just "don't ask Yahoo the same static question twice."
  2. Historical price/FX series (`performance._daily_series`) were fetched fresh per snapshot too, each a narrow ~10-day window around one `as_of` date -- even though several snapshots (one per Timeframe pill, each needing the *same* shared "window end" date -- see above) request heavily overlapping ranges. Fixed with `_cached_daily_series`: one widening per-ticker cache that grows to cover whatever's been asked for so far, so a nearby later request is served from what's already fetched instead of triggering its own round trip. Rolled out to every call site that used to call `_daily_series` directly for a value that's genuinely reusable across snapshots (`cost_basis.py`'s `total_pnl` and `_build_fx_cache`).
  3. A real bug in that new cache, caught by timing a *supposedly warm* second call and finding it just as slow as the first: the cache-hit check compared the cached data's real max date against a deliberately *future* requested `end` (callers pad it a day past `as_of` so an `.asof()` lookup doesn't land exactly on the last index entry) -- but Yahoo never returns bars past today regardless of what's asked for, so that comparison could never be satisfied and the cache never once hit. Fixed by capping the comparison at today, the actual ceiling the cache can ever reach.
  - **Prefetched, not just cached**: Matteo asked for the wait to happen once, while the Account Statement itself is loading, rather than the first time each pill is clicked. `app.py`'s `prefetch_all_timeframe_pnl` computes the (at most five distinct: one shared window-end, one per Timeframe's window-start) P&L snapshots right after `load_and_reconstruct_value_history` returns, under its own spinner ("Computing profit/loss for every timeframe..."), so every Timeframe pill is already warm by the time the page is interactive. Backed by `compute_pnl_snapshot`, a new `@st.cache_data` function keyed on `(events, as_of)` -- `compute_windowed_pnl` now composes two calls to it instead of calling `cost_basis.windowed_pnl` directly, specifically so Streamlit's cache recognizes the shared end-of-window snapshot as the *same* call across all four pills, not four separate ones.
  - **Result on real test data**: after the fixes above and a full prefetch, every pill (including ones never directly clicked before) resolves in ~1.3-1.7 seconds measured at the raw Python level -- and near-instantaneously in the running app itself, since `compute_pnl_snapshot`'s `st.cache_data` layer serves the already-computed result directly rather than re-running the FIFO computation at all.

## Suggested repo structure
`app.py` is now a *true* entry point, not just a short orchestrator: page config plus Streamlit's multipage navigation (`st.navigation` + `st.Page`, callable-based -- no `pages/` directory, since a plain Python function works directly as a page and keeps everything importable from `views/` like every other view). Each registered page is its own independent script run with no inherited local variables from `app.py` or from any other page -- only `st.session_state` persists across navigation -- so the old single-run "orchestrator computes shared state once, tabs consume it" shape (see the previous entry in this file) doesn't carry over as-is. `state.py`'s `load_dashboard_state()` is what replaces it: the exact same shared setup (loading, sidebar controls, banners), called fresh at the top of *every* page's own render function instead of once in `app.py`. `aggregations.py` and `theme.py` are unaffected by this -- still shared logic more than one view depends on.
```
portfolio-dashboard/
  app.py              # Entry point: page config, st.Page/st.navigation setup, pg.run() -- nothing else
  state.py              # load_dashboard_state(): shared per-page setup (loading, sidebar controls, banners), called by every page
  aggregations.py       # Shared breakdowns (sector/region/country/continent/asset-type/currency) + concentration/drift/overlap flag logic
  theme.py               # Chart color palette + chart_theme() -- formatting.py's counterpart for color, not numbers
  views/
    overview.py           # Overview page (default/landing): Positions + a compact Allocation donut side-by-side, Rebalance below when ETFs-only
    allocation_page.py     # Allocation page: the full donut + holdings list -- Overview's compact donut "Show more"s here
    positions.py          # Positions tab content: paginated table, Show more/less
    allocation.py          # Full Allocation content (view selector, donut, list) -- called by allocation_page.py
    rebalance_view.py       # Rebalance section (named to avoid colliding with the root rebalance.py it calls into)
    dividends.py            # Dividends section (currently hidden -- see state.py's SHOW_DIVIDENDS_SECTION): Yahoo-estimate view only
  parser.py             # DEGIRO Portfolio.csv -> DataFrame (positional column parsing, European numbers)
  enrichment.py        # ISIN resolution, sector/region/type lookup, ETF overlap logic
  rebalance.py          # Pure-computation rebalancing calculator (no API calls, no caching) -- called by views/rebalance_view.py
  formatting.py          # European-style euro/percent formatting, used everywhere a value is displayed
  components/
    donut_chart.py       # Reusable interactive donut (raw Plotly.js via st.components.v1.html); render_donut(..., compact=True) for the Overview page's small one
  storage.py            # SQLite read/write for snapshots (local version only)
  overrides.csv         # Manual isin,ticker,region escape hatch for enrichment edge cases
  fund_regions.csv     # Cache: ISIN -> country/region weightings, scraped from justETF
  fund_ter.csv          # Cache: ISIN -> TER, scraped from justETF (same call as fund_regions.csv)
  requirements.txt
  venv/
```
`ledger.py`, the project-root `performance.py`, `cost_basis.py`, and `views/performance.py` all used to be listed here too (the Performance view's data pipeline) -- removed along with the feature itself, see "Performance view (built, then fully removed)," above.

**Cross-page navigation, and why the Allocation `st.Page` object lives in session_state**: `views/overview.py`'s "Show more" link (`st.page_link`) needs a reference to the Allocation page's actual `st.Page` object, not just a label -- but that object only exists once `app.py` calls `st.Page(render_allocation_page, ...)`, and `views/overview.py` can't import it from `app.py` directly (importing `app.py` would re-run its own top-level code, `st.navigation(...).run()` included, as a side effect of the import -- not just fetch a variable). `app.py` stashes it in `st.session_state["_allocation_page"]` right after constructing it, and `views/overview.py` reads it back out from there instead.
